# 동기화 아키텍처 제안

여러 PC와 휴대폰에서 같은 이력·작업을 보기 위한 설계안. **구현 전 검토용**이며,
결정이 필요한 항목은 마지막에 모아두었다.

---

## 1. 결론 먼저

| 항목 | 제안 |
|---|---|
| 저장소 | **Google Drive의 앱 전용 폴더**(`appDataFolder`). GCS 아님 |
| 인증 | OAuth 2.0 + PKCE. 설정 화면에 계정·키를 입력받지 않음 |
| 토큰 보관 | Electron `safeStorage`(Windows DPAPI / macOS 키체인 / Linux libsecret) |
| 충돌 처리 | 데이터 종류마다 다름. 로그는 합집합, 작업·규칙은 레코드 단위 |
| 진행 순서 | **이력 → 스키마 정비 → 작업·규칙** 3단계 |

가장 중요한 사실 하나: **지금 구조로는 작업 목록을 동기화할 수 없다.**
이유는 5장에 있다. 이력만이라면 훨씬 간단하다.

---

## 2. 왜 Drive이고 왜 GCS가 아닌가

**Google Cloud Storage는 이 용도에 맞지 않는다.**

- 접근하려면 서비스 계정 키가 필요한데, 데스크톱 앱에 넣으면 그 키가 사용자
  PC에 그대로 놓인다. 추출되면 버킷 전체가 열린다
- 저장 요금을 개발자가 낸다. 사용자가 늘수록 비용이 는다
- 사용자 입장에서 "내 데이터가 개발자 계정에 쌓인다"는 것도 설명하기 어렵다

**Drive `appDataFolder`가 정석이다.**

- 사용자가 자기 계정에 로그인하고, 자기 용량을 쓴다
- 앱이 만든 파일만 보인다. "내 드라이브 전체 접근"이 아니며 승인 화면에도
  그렇게 표시된다(`drive.appdata` 스코프)
- 사용자 드라이브 목록에 폴더가 보이지 않아 실수로 지울 일이 적다
- 연결 해제는 사용자가 구글 계정 설정에서 언제든 할 수 있다

대안으로 **파일 하나만 얹는 방식**(사용자가 직접 드라이브/원드라이브 폴더를
지정하고 앱은 거기 읽고 쓰기)도 있다. OAuth가 아예 필요 없어 가장 단순하지만,
휴대폰(PWA)에서는 쓸 수 없다.

---

## 3. 인증 — 설정에 계정을 넣지 않는다

설정에는 **`Google Drive 연결` 버튼 하나**만 둔다.

### 데스크톱(Electron)

1. 버튼을 누르면 **시스템 브라우저**가 열려 구글 로그인 화면으로 간다.
   앱은 비밀번호를 보지도 저장하지도 않는다
2. 리다이렉트는 `http://127.0.0.1:<임의포트>`. 메인 프로세스가 잠깐 작은 HTTP
   서버를 띄워 인증 코드를 받는다
3. **PKCE**를 쓴다. 데스크톱 앱의 client secret은 어차피 비밀이 될 수 없으므로,
   보호는 PKCE가 담당한다 (구글이 설치형 앱에 권장하는 방식)
4. 받은 **refresh token은 `safeStorage`로 암호화해서 저장**한다. 평문 JSON에
   두면 파일을 복사하는 것만으로 계정이 넘어간다

### 휴대폰·브라우저(PWA)

루프백 리다이렉트를 쓸 수 없다. Google Identity Services의 토큰 흐름을
페이지 안에서 쓰고, **액세스 토큰만 메모리에 유지**한다(새로고침하면 재인증).
같은 계정이므로 데이터는 그대로 이어진다.

### 권한 범위

`https://www.googleapis.com/auth/drive.appdata` 하나. 그 이상 요구하지 않는다.

## 4. 무엇을 동기화하나 — 세 계층

| 계층 | 성격 | 충돌 위험 | 난이도 |
|---|---|---|---|
| **이력** (`logs/*.tsv`) | 추가 전용, 날짜별 파일 | 매우 낮음 | 낮음 |
| **규칙** (`rules.json`) | 소량, 드물게 변경 | 낮음 | 중간 |
| **작업** (`tasks.json`) | 자주 변경, 순서가 의미를 가짐 | **높음** | 높음 |
| 설정 (localStorage) | 기기별 취향 | — | 동기화 안 함 권장 |

설정(테마·날짜 형식·언어)은 **기기마다 다른 게 자연스럽다.** 데스크톱은 다크,
폰은 라이트일 수 있다. 태그 프리셋 정도만 공유 대상으로 볼 만하다.

## 5. 핵심 문제 — 지금 구조로는 작업을 동기화할 수 없다

현재 레코드에 있는 필드:

```
task: id, content, tags, startDateTime, targetDateTime, completed,
      completedAt, createdAt, highlighted, notificationEnabled,
      ruleId, status, leadMinutes
rule: id, content, tags, freq, interval, byWeekday, anchorDate,
      startTimeOfDay, targetTimeOfDay, enabled
```

**없는 것이 셋이다.**

1. **`updatedAt`** — 어느 쪽이 최신인지 판단할 근거가 없다
2. **삭제 표식(tombstone)** — A에서 지운 작업이 B의 사본을 통해 되살아난다.
   지움은 "없음"으로 표현되는데, 없음은 "아직 못 받았음"과 구분되지 않는다
3. **명시적 순서** — 지금 순서는 **배열의 위치**다. 두 기기가 각각 순서를
   바꾸면 병합할 방법이 없다

여기에 저장 방식이 **파일 통째로 덮어쓰기**라, 늦게 저장한 쪽이 상대의 변경을
전부 지운다. 이 셋을 해결하지 않으면 작업 동기화는 **데이터 유실 장치**가 된다.

### 필요한 스키마 변경

```jsonc
{
  "id": "task-...",
  "updatedAt": "2026-08-08T10:00:00+09:00",  // 모든 수정에서 갱신
  "deletedAt": null,                          // 지우면 시각을 기록(레코드는 남김)
  "order": 1024,                              // 명시적 순서 (아래 참고)
  "...": "기존 필드"
}
```

**순서**는 배열 위치 대신 숫자를 둔다. 두 항목 사이로 옮길 때 그 중간값을
넣으면(1024와 2048 사이 → 1536) 다른 기기의 이동과 섞여도 순서가 유지된다.
정수 인덱스는 항목 하나를 옮길 때마다 뒤 전체가 바뀌어 충돌을 만든다.

**tombstone**은 30일쯤 두고 지운다. 그 기간보다 오래 꺼져 있던 기기는 삭제를
못 받을 수 있는데, 실무적으로 감수할 만하다.

## 6. 두 가지 설계

### 모델 A — 공유 문서 병합 (단순)

Drive에 `tasks.json`, `rules.json`, `logs/YYYY-MM-DD.tsv`를 그대로 둔다.

```
동기화 = 원격 읽기 → 로컬과 병합 → 원격 쓰기 → 로컬 저장
```

병합 규칙:
- **작업·규칙**: id로 묶고 `updatedAt`이 큰 쪽 채택. `deletedAt`이 있으면 삭제
- **로그**: 줄 단위 **합집합** 후 타임스탬프 정렬. 각 줄이 사실상 고유하므로
  여러 번 합쳐도 결과가 같다(멱등)

**약점**: Drive에는 조건부 쓰기(If-Match)가 없다. 두 기기가 거의 동시에
읽고 쓰면 한쪽 변경이 사라지는 창이 남는다. 창은 좁고 다음 동기화에서 대부분
자가 복구되지만, **0은 아니다.**

### 모델 B — 기기별 변경 로그 (견고)

각 기기는 **자기 파일에만** 쓴다.

```
appDataFolder/
  snapshot.json            주기적으로 접은 스냅샷
  changes-<기기ID>.jsonl   기기마다 하나. 추가 전용
  logs/2026-08-08.tsv      이력은 그대로
```

각 줄은 하나의 조작이다:

```jsonl
{"op":"upsertTask","at":"2026-08-08T10:00:00+09:00","task":{...}}
{"op":"deleteTask","at":"2026-08-08T10:05:00+09:00","id":"task-1"}
```

동기화 = 내 파일 이어쓰기 + 남의 파일 받아서 `at` 순으로 재생.

**쓰기 충돌이 원천적으로 없다.** 아무도 남의 파일을 건드리지 않기 때문이다.
대신 파일이 계속 자라므로 **압축(compaction)**이 필요하다 — 오래된 조작을
`snapshot.json`으로 접고 변경 로그를 비운다. 압축은 한 기기가 주도해야 해서
그 순간만 조율이 필요하다.

### 권장

**이력만 한다면 모델 A로 충분하다.** 로그는 합집합 병합이라 애초에 충돌이
없고, 위에서 말한 창도 로그에는 해당하지 않는다.

**작업까지 간다면 모델 B가 맞다.** 모델 A의 유실 창은 "가끔 한 건 사라짐"으로
나타나는데, 이런 종류의 버그는 재현이 안 돼서 신뢰를 크게 깎는다.

## 7. 언제 동기화하나

- 앱 시작 시 1회
- 변경 후 **디바운스**(예: 5초). 매 키 입력마다 올리지 않는다
- 창이 포커스를 얻을 때(다른 기기에서 바뀌었을 수 있다)
- 수동 `지금 동기화` 버튼 — 자동 동기화는 **언제 끝났는지 보이지 않으면
  불안하다.** 마지막 동기화 시각을 설정에 표시한다

원격 변경 감지는 Drive 파일의 `md5Checksum`이나 `modifiedTime`을 먼저 조회해
바뀐 것만 내려받는다. 매번 전부 받으면 모바일 데이터를 낭비한다.

---

## 8. 실패했을 때

동기화 기능에서 가장 중요한 부분이다. **실패는 정상 경로다.**

| 상황 | 동작 |
|---|---|
| 오프라인 | 로컬은 평소대로 동작. 큐에 쌓고 연결되면 보냄 |
| 토큰 만료 | 자동 갱신. 실패하면 조용히 끄고 재연결 안내 |
| 권한 회수 | 동기화 중단, 로컬 데이터는 그대로 유지 |
| 병합 중 오류 | **원격을 건드리지 않고 중단.** 반쯤 쓰다 마는 것이 최악 |
| 용량 초과 | 이력 업로드만 중단하고 알림 |

로컬이 항상 진실의 원본이고 원격은 사본이라는 원칙을 지킨다. **동기화가
실패해도 앱은 평소처럼 쓸 수 있어야 한다.**

---

## 9. 단계별 계획

| 단계 | 범위 | 얻는 것 | 규모 |
|---|---|---|---|
| **1** | OAuth 연결 + **이력만** 동기화 | 어느 기기에서든 통계·이력 조회 | 며칠 |
| **2** | 스키마 정비(`updatedAt`·tombstone·`order`) + 마이그레이션 | 동기화 없이도 이득: 삭제 이력, 정렬 안정 | 며칠 |
| **3** | 작업·규칙 동기화(모델 B) | 진짜 다기기 사용 | 1~2주 |
| **4** | 압축, 충돌 진단 화면 | 장기 운영 | — |

**1단계만으로도 원래 말씀하신 "어디서든 이력 확인"은 충족된다.**
2단계는 동기화를 안 하더라도 앱 자체가 좋아지므로 따로 해도 손해가 없다.

---

## 10. 결정이 필요한 것

1. **범위** — 이력만인가, 작업 목록까지인가
   (이력만이면 1단계로 끝. 작업까지면 2·3단계 필수)
2. **Google Cloud 프로젝트** — OAuth 클라이언트 ID를 발급하려면 콘솔에
   프로젝트를 만들고 앱을 등록해야 한다. 외부 사용자에게 배포하려면 심사가
   필요할 수 있다. 본인만 쓴다면 테스트 사용자로 등록하면 충분하다
3. **Drive 외 대안** — OAuth 없이 "사용자가 지정한 동기화 폴더에 파일을 둔다"
   방식도 있다. 훨씬 단순하지만 휴대폰에서는 못 쓴다
4. **설정 동기화 여부** — 테마·언어까지 맞출 것인가, 기기별로 둘 것인가

## 부록 — 지금 코드에서 손볼 곳

| 파일 | 변경 |
|---|---|
| `main.js` | Drive 클라이언트, OAuth 루프백 서버, `safeStorage` 토큰 보관 |
| `preload.js` | `connectDrive` / `syncNow` / `getSyncStatus` 노출 |
| `renderer.js` | 저장 시 `updatedAt` 기록, 삭제를 tombstone으로, `order` 도입 |
| `recurrence.js` | 변경 없음 |
| 설정 화면 | 연결 버튼, 마지막 동기화 시각, 연결 해제 |

`tasks.json`의 저장 경로가 이미 IPC 한 곳(`save-tasks`)으로 모여 있어
`updatedAt` 기록을 끼워 넣기 좋다. 반면 **순서가 배열 위치에 의존**하는 코드가
여러 곳(`moveTask`, `repositionTask`, `renderExpandedTasks`)에 있어
`order` 도입이 2단계에서 가장 손이 많이 가는 부분이다.
